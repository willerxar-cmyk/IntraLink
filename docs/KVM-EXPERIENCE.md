# KVM experience: connection cards, local cursor and spatial transitions (preview.13)

## Operator flow

1. Choose BASE (the central keyboard/mouse) or CLIENT (the device to control). A role never grants access. Existing full identity/manual pairing remains available.
2. Android BASE: Copy BASE connection card. Android CLIENT: Copy CLIENT connection card, confirm the private address and port, then Copy connection card. The active network's unique private IPv4 is prefilled when available; otherwise enter it manually. Transfer the public card to the other owner via a trusted channel. On desktop use `intralink connection-card` (BASE) or `intralink connection-card --address PRIVATE_IP:45100` (CLIENT). A Hybrid explicitly chooses which role to advertise by supplying or omitting the route.
3. Android: Pair a BASE/CLIENT, Paste connection card, set the local peer label and unlock the local vault. Desktop: `intralink pair-card --name DEVICE_LABEL`, paste the card. Verify the complete identity independently; confirm on both devices. The card is only an unsigned convenience representation of existing public fields, not an access token, signature, discovery result, authorization, or proof of identity ownership. No passphrase, private key, stored grants, or automatic enrollment. Canonical syntax and limits in crates/intralink-core/src/pair_card.rs. Copy/paste only on explicit local action.
4. Choose the independently approved scope: screen only (existing MediaProjection UI), input preview (below). Simultaneous screen+input is still future work; the existing registry and vault lock deliberately exclude overlapping sessions. The actual Windows/Linux input adapters remain separate and optional.

## Android input-only preview

Open Mouse and keyboard preview under a previously paired inbound BASE, review its full identity and enter the passphrase. Press Approve mouse and keyboard preview locally. The client will bind only the selected private route and listen for the pinned BASE. This is a normal non-exported foreground Activity, not a persistent service. No new Android permission, AccessibilityService, ADB injection, IME, overlay permission, screen projection or other-app control. Input is scoped strictly to the test canvas: normalized pointer, left/right/middle button state, bounded scroll counter and local ASCII text with a bounded physical HID subset via the Android virtual keyboard map. Modifier chords and unsupported text keys do not execute system shortcuts. The canvas has a visible high-contrast arrow with exact normalized hotspot; the glyph points inward at the edges so it remains visible. The local Stop button and identity/password form are outside the remote canvas. No recording or text persistence.

Use a separately approved Windows BASE with `intralink input workspace --device DEVICE_LABEL` (input-preview build), or Linux focused source with input-x11-preview. One input lease at most, 60 seconds after handshake, existing pinned input/1 ALPN, single outstanding delivery and ACK only after local UI acceptance. Native Rust verifies role, saved full peer identity, private address, reloaded vault and session reservation. JNI calls the bounded foreground app sink; main-thread dispatch checks current approval, focus, attachment, visibility, ordered sequence and 220ms event expiry. The worker rejects a timeout and closes the connection; no retries. On deactivate/end, local stop, focus/pause/destroy, disconnect or timeout, release app-owned held state and hide the cursor. Existing screen/probe grants do not silently confer input scope. No claim of cross-app input.

The physical generated acceptance uses the normal app canvas and normal runInput JNI through a test-only Activity launch, a fresh encrypted temporary vault and generated events from the Windows Rust example. It checks actual cursor pixels, exact state, typed test characters, click, scroll, release and revocation. Use only the owner-selected physical device and an unlocked foreground display. It does not exercise the manual pairing/approval UI end-to-end or arbitrary Android apps.

## Spatial arrangement and portal

Windows focused KVM pad (`intralink input workspace --device CLIENT1 --device CLIENT2 --spatial`) starts SAFE. The local card is numbered 0, remote cards 1..8 remain tied to their paired identities. Drag a populated card onto another cell while SAFE to swap or place it in empty space; F9 arms, F12 returns local and disarms. The arrangement is session-local in this preview. Move within the visible pad, never outside it. One active host at a time. Existing 80ms dwell and old-host release/new-host activation acknowledgments remain authoritative. A held key or mouse drag across zones releases and disarms; it never transfers a partially held chord or drag implicitly.

The local portal renderer samples only a bounded patch (radius up to 44px, 220ms), applies a small swirl/lens and colored ring, then clears; blue while a shared-edge transition is pending, green only following confirmed activation. This is a visual cue in the application pad, not a desktop compositor effect. It does not change hit tests, cursor coordinates, input grants, capture pixels or network data. The OS's local cursor remains visible. No continuous full-screen effect or busy spin.

Core screen_topology.rs separately provides deterministic rectangular topology for upcoming physical-edge native adapters. It validates one BASE and up to eight CLIENTs, unique identities, signed positions and mixed sizes, no overlaps; transfers only across truly touching edges with overlapping tangent intervals, preserves tangent position and arrives one pixel inward. Gaps and corners fail closed. DPI units and native monitor enumeration still require integration; no physical desktop hook is added.

## Future acceptance

Persist user-defined named layouts; visual editor with actual screen dimensions, offsets and preview; native topology-aware edge routing with emergency release and raw-input permissions; CLIENT cursor in the correct logical/physical coordinates, system-supported input adapter and independent consent on Android. Design separate read-only, input-only and simultaneous grants. Use standard platform APIs, never privileged injection, unattended control or bypass of OS authorization. Android system-wide gestures/keyboard require separately designed user-enabled platform permissions and qualification; investigate supported Bluetooth HID or Accessibility/IME alternatives with minimal scope, clear disclosure and immediate revocation. Do not conflate gesture injection or app text editing with native physical mouse/keyboard semantics. H.264 remote admission remains separate from the proven portable media path.

## Graphical signed enrollment (2026-11-28)

Desktop-preview Windows/X11 builds accept the opt-in `--gui` flag for `invite`, `accept-invite`, `confirm-invite` and `connection-card`. The graphical review presents both complete 64-digit hex identities, full validated routing host (up to 253 ASCII bytes, wrapped without truncation), UDP port, validity/expiry, scope and local peer label. Exact lowercase/case-sensitive values are also printed in the terminal; the compact bitmap font renders labels and hexadecimal digits in uppercase. Confirm identity ownership independently over a trusted channel; a self-signed code does not establish human ownership. Check the verification box or release Space, then use the distinct confirmation button or release Enter. Escape, Cancel, window close or deadline aborts without saving; loss of window focus clears verification and held-control state. Already-held, mixed mouse/key or overlapping gestures cannot approve. New invitation review lasts at most 300 seconds; existing invitation review also stops at actual expiry. The signed accept/confirm code is verified by the existing Rust vault and checked again at mutation. No network access, listener, camera, clipboard read, screen/input authorization or new protocol is introduced by these windows.

A generated QR uses the complete existing signed offer/acceptance, integer module scaling and a four-module quiet zone. Generate the QR before the local encrypted write; after successful save print the exact code and show the window. The window closes at actual expiry or at most five minutes. A presentation failure after saving is reported explicitly and does not claim a rollback. The public `connection-card --gui` uses the same renderer but is prominently labeled unsigned and no access grant. Closing a displayed code does not revoke an issued offer or saved grant; use the existing cancel/revoke commands when needed. Passwords remain in the local no-echo terminal; after saving, the password and profile are dropped before displaying the code. The local vault lock stays held until the window closes. Existing terminal text and terminal `--qr` workflows remain; `--qr` and `--gui` are mutually exclusive. No native camera reader or mobile signed-invite integration yet: transfer the exact text through a trusted channel or use an independently trusted reader and paste the payload, never a shortened identity. Android's existing unsigned connection-card workflow remains separate. This is a graphical review/QR display, not a completely terminal-free wizard.

Example: after both devices have exchanged and verified full public identities, use on CLIENT `intralink invite --controller-id BASE_PUBLIC_ID --host CLIENT_PRIVATE_IPV4 --port 45100 --gui`; transfer the signed offer. On BASE `intralink accept-invite --name client --gui`; transfer the signed acceptance. On CLIENT `intralink confirm-invite --name base --gui`. The three operations create only the existing directional pairing records. Each actual session still needs its separately authorized capability. See benchmarks/kvm-graphical-pairing-20261128.txt.
