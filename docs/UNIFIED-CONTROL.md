# Unified Windows screen and input controller (preview)

Use the existing signed pairing and independently approved CLIENT listeners from [SESSION-COEXISTENCE.md](SESSION-COEXISTENCE.md). The current Windows BASE may now use one command and window for one paired CLIENT:

    intralink control-desktop --choose --input-port 45101
    intralink control-desktop --device client --input-port 45101

This command is available with Windows input-preview (WGC/CUDA not required). The input port is mandatory, must differ from the saved screen listener port, and is a temporary route hint only. Existing v8/v10/v11/v12 view selection and receiver ceilings are available; use the options that the locally approved screen listener supports. The input listener must explicitly use input/2 (`input host --display-geometry`); no silent fallback to input/1. The one-device graphical selector does not grant or connect a capability. Existing separate commands and up-to-eight-device workspaces are preserved.

## Operation

Unlock the same existing BASE vault once, select the exact paired CLIENT, and review the full pinned identity and separate routes in the terminal. The visible native window opens SAFE with both capabilities OFF. START SCREEN and START INPUT are distinct complete local click gestures; each CLIENT listener still requires its own explicit local approval, and each gets its own independent endpoint, lease and worker. Neither button grants the other capability. Reopening an ended/failed capability requires another explicit click and a new locally approved CLIENT listener. No automatic reconnect. The combined window reserves both profile capability lanes in fixed nonblocking order until it closes, even if a lane is stopped; do not run duplicate desktop commands with the same profile in parallel. The vault stays read-only, and the retained identity is used only for explicitly started sessions.

- SCREEN ONLY: start screen and leave input off. No remote keyboard or mouse.
- INPUT ONLY: start input with screen off; a clearly labelled proportional primary-display pad appears. Click ARM INPUT, then move into the pad with no keys/buttons/wheel held. Input/2 geometry is from the current pinned session.
- BOTH: start both. Direct visual control is **disabled** until independently verifying that the approved video source is the same CLIENT primary monitor reported by input/2. Click VERIFY PRIMARY then CONFIRM MATCH, only after comparing the actual CLIENT primary with the displayed video. Existing screen ALPNs do not attest the selected monitor ID, so this is human confirmation, not remote hardware proof. A new session, changed video dimensions, lost connection, stale sample, or changed input metadata invalidates the relevant control/review. Click ARM INPUT, enter the image content with neutral input, wait for acknowledged Activate and initial Move, then use mouse/keyboard. Toolbar clicks are local. The render mapping accounts for the host's aspect-preserving letterbox and the BASE window's scaled presentation; black bars are not control areas. Unsupported OS-reserved keys stop/release control. This focused MiniFB path retains snapshot-based key/button/wheel forwarding, not lossless native event capture.

F12, leaving the active content, focus loss, or a changed control region releases input and requires explicit re-arm. A stale video (the existing one-second no-update notice, or absence of a received Frame/Repeat observation for two seconds) prevents direct control; this is a local receive-health guard, not a guarantee of actual end-to-end frame age. A stopped screen is cleared immediately from the presentation and input remains separately connected SAFE; re-arm the input-only pad explicitly. STOP INPUT sends Deactivate if active and End using bounded ACK, then closes only the input endpoint. STOP SCREEN releases direct control before stopping only the screen worker/endpoint. A failed input release cancels the input connection rather than guessing the remote state. Closing or Escape stops both; input End/closure is handled before joining the decoder. Actual disconnect cleanup remains subject to the existing receiver-owned release policy and network deadlines.

## Rendering and scope

One 1920x1080 composite canvas, with reusable 960x540 chrome and a cached integer horizontal sampling map. Remote pixels are presented only in the bounded content area and never used as local controls. The immutable decoded snapshot is held only during presentation; the existing ordered workspace decoder/transport pipeline remains unchanged. The renderer repaints chrome on state changes and the image on new decoded frames; no new full-frame resize allocation per tick. Nearest-neighbor preview scaling is explicit, and the displayed image is smaller than a full native 1080p canvas because of the local toolbar. No certified sustained FPS, hardware latency, simultaneous native capture/injection, global hooks, or transparent KVM claim.

The initial integrated window is Windows BASE only, one selected CLIENT at a time. Windows CLIENTs use the existing separate consented screen/input host commands. Linux X11 and Android retain their current UI and capability policy. A single CLIENT-side combined launcher, authenticated binding of video monitor identity to input/2, multi-device unified viewer, fully terminal-free setup, and physical acceptance remain pending.
