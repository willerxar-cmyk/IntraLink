# Wire protocol

## Implemented: `intralink/probe/1`

An Iroh connection uses authenticated QUIC with TLS. The controller dials a pinned endpoint ID and explicitly resolved socket address. The host accepts one incoming authenticated connection and checks its endpoint ID against the locally approved controller ID. No 0-RTT path is used by the application. The controller opens a single bidirectional stream and sends exactly `INTRALINK/1 PING`, then finishes its send stream. Host reads at most 32 bytes through stream completion, checks exact equality, writes `INTRALINK/1 PONG`, and finishes. Controller checks exact equality and closes. No extensible remote command language. Handshake deadline: 10 seconds; per-session deadline: 20 seconds. Host CLI has a 120-second incoming wait; the original helper uses a 20-second incoming wait. A DNS lookup has a 5-second deadline. The host is not a long-running service. v0.3 uses persistent locally approved directional grants from IntraVault; the host still requires explicit local start and handles only one selected controller. The controller supplies a bounded set of candidate addresses to Iroh while preserving the same pinned identity. No pairing or grant mutation messages are carried on the wire. Offline enrollment is documented in [ENROLLMENT.md](ENROLLMENT.md); it is not a new remotely callable endpoint. Optional LAN DNS-SD supplies routing hints only.

## Experimental `intralink/view/8`

The host binds only the view v8 ALPN. The controller dials the saved DNS/IP route and pinned host public key. The host validates the locally selected inbound controller before accepting one bidirectional stream. No early data or remotely initiated authorization. A fresh local approval is required for every session. Both endpoints must support v8; v1 through v7 are not negotiated or silently accepted.

Wire sequence:

1. Controller sends 17 bytes: 16-byte prefix `INTRALINK/8 VIEW` followed by one mode byte (`0` JPEG, `1` basic tiles/JPEG, `2` compact tiles/lossless keyframes/JPEG), without FIN. The host verifies the prefix and requires the locally approved mode before requesting capture. Unknown or mismatched modes fail closed; subsequent bytes have only the fixed acknowledgment interpretation below.
2. Host returns eight configuration bytes: output height (u16 BE; 540/720/1080), maximum target FPS (u8; 1–60), JPEG quality (u8; 35–90), duration (u16 BE; 1–3600 seconds), one byte fixed at 8 (record credit), one mode byte matching the request. Width is height × 16/9. The host selects the configuration; the viewer rejects invalid values and mode mismatch before allocation.
3. Host sends records, each starting with u32 BE: `0` is end, `0xffffffff` is a verified repeat of the most recent image, `0xfffffffe` means no new native update was observed, and `1..=2097152` is the length of a changed media payload. All other lengths are invalid. The media payload has a one-byte tag: 0 JPEG keyframe, 1 absolute RGB tile delta, 2 independent lossless full-grid keyframe (Compact only). The decoder rejects a delta before a keyframe or outside hybrid mode; compact entry types and tag 2 are only allowed in mode 2. A tag 2 keyframe must contain every tile exactly once, including edges, and is bounded to 512 KiB; the current sender attempts it with a 128 KiB policy budget. Full validation precedes canvas resize or mutation. See [TILES.md](TILES.md) for the bounded layout. The transport rejects repeats and no-update records before a changed record. Neither triggers decoding. No-update is not a claim of unchanged pixels, source health or frame freshness.
4. For each changed media record, repeat or no-update the controller sends a u32 BE acknowledgment with the one-based record index in bits 0–30 and background-priority hint in bit 31 (0 foreground, 1 background). The hint is applied only after ordered receipt validation; it can reduce sampling to at most 5 FPS but cannot elevate the approved FPS. A bounded receipt pump reads independently of capture. The host may send up to eight records without consuming receipts. When credit is exhausted, it waits for the next exact ordered ACK before requesting another capture; duplicate, skipped or invalid receipts fail at the next read. At most one capture request is in progress. ACKs acknowledge receipt/ordered-queue acceptance only, not decoding, rendering or permission. An authorized malicious peer can precompute sequence numbers; this is a backpressure mechanism for conforming peers, not proof of actual reception. No other controller action is implemented.
5. After stopping capture, host drains all outstanding ordered receipts with a single five-second cleanup budget, then emits the zero end marker and FIN. Viewer requires FIN with no trailing server bytes, finishes its send stream and closes. The host consumes no further commands and waits briefly for close. Local cancellation can abort either side without a graceful end.

Bounded application data: 2 MiB per changed frame, at most `duration × FPS` records (216000 maximum), acceptance 120s, TLS handshake 10s, per-I/O and capture-response waits at most 5s, negotiated viewer deadline. A host does not start a new record after its capture deadline. Native calls cannot themselves be interrupted by the async timeout. A conforming reader that withholds acknowledgments stalls capture at the eight-record window (up to 16 MiB media payload, not total memory); a malicious paired peer can pre-acknowledge predicted sequence numbers, so this is not a security boundary. QUIC and OS buffers still exist. No input, file, shell, recording or capability-upgrade commands. The vault and diagnostic protocol are unchanged. See [DESKTOP.md](DESKTOP.md).

## Proposed expanded session protocol (not implemented)

Build on separately versioned ALPNs. Versioned, bounded messages with typed capabilities; no generic arbitrary command dispatcher. Negotiate version and feature set, evaluate locally configured authorization per capability, and bind all grants to the authenticated controller and session. Enforce least privilege, use explicit permission scopes, and fail closed on unknown critical versions/capabilities. Handle cancellation and revoke active sessions. Control, media, files and monitoring use distinct flows and independent backpressure. Prioritize user input/control over bulk data; enforce per-stream and per-session resource limits. Disable privileged actions in early data. Define stable message schemas only after a threat-model review; do not freeze a production wire format based on this diagnostic.

In v0.13 the sender may sample more slowly after consecutive repeat records. No new control messages are introduced, and the receiver does not infer fixed frame intervals. Sequence numbering, ordered delivery, credit and deadlines remain unchanged. See [PERFORMANCE.md](PERFORMANCE.md).

Wire v8 adds one reserved no-update header with no payload and one ordered ACK/credit. No-update is counted separately from repeats and changed frames, consumes the same negotiated record budget, and permits adaptive pacing without asserting that the pixels match. The Host WGC preview imposes a conservative 15-second no-observed-readback watchdog; the receiver shows a local last-frame notice after one second of consecutive no-update observations. Both peers must upgrade; the probe ALPN and vault schema are unchanged.

## Experimental isolated H.264 transport v9

The normal desktop CLI defaults to `intralink/view/8` and offers JPEG/Tiles/Compact; its explicit adaptive mode binds the separate v10 ALPN. The H.264 diagnostic binds a separate `intralink/view/9-h264` ALPN on loopback only; no real Host command exposes it. Both endpoints use freshly generated pinned identities for the synthetic diagnostic. The existing transport engine, capture demand, receipt credit and deadline logic are shared; no v8 wire bytes change.

After the exact 17-byte `INTRALINK/9 VIEW` prefix plus mode byte 3, the viewer sends a 12-byte exact profile offer. The Host compares it to the locally supplied profile before issuing any capture demand and echoes it. Layout: height u16 BE (540/720/1080), FPS u8 (1-60), profile u8=1 (H.264 High progressive 8-bit 4:2:0 BT.709 limited), duration u16 BE (1-3600), credit u8=8, reserved u8=0, target bitrate u32 BE (500000-20000000 bits/s). The target bitrate is not a strict measured network ceiling. Both peers reject unsupported or mismatched values and ALPNs. Width is height times 16/9.

The outer four-byte record length and receipt format are unchanged. H.264 changed records carry an eight-byte envelope: tag 0x48, version 1, IDR flag (0/1), reserved byte 0, coded picture sequence u32 BE, followed by one Annex B access unit (max 2 MiB minus envelope). Coded picture sequence starts at 1 and is distinct from receipt sequence. No-update/repeat records carry no access unit and do not advance coded sequence. The structural guard requires AUD first, a single I/P slice, bounded NAL count and metadata, SPS/PPS at every IDR with consistent parameter IDs and identical parameter sets after the first IDR, no B slice, no mixed/missing pictures, and periodic IDR at most FPS coded pictures apart. Gaps, duplicates, changed parameter sets or malformed envelopes terminate the session without a receipt or consumer callback for the bad record. No arbitrary resynchronization or remote reset command; a fresh session starts from IDR.

The structural Annex B/header guard is deliberately not a full H.264 syntax validator: it does not prove complete SPS geometry/VUI, all slice syntax or native-decoder safety. The diagnostic passes only byte-identical previously generated local fixture packets to NVDEC. No network-supplied arbitrary compressed bytes reach the driver. Native input security review, full SPS/profile validation, per-session decoder isolation, cancellation, actual WGC-to-NVENC compatibility and ordered native presentation are mandatory before enabling H.264 for physical sharing. No remote command, input or permissions were added.

### Restricted SPS/PPS validation

Both v9 peers now parse bounded parameter sets with safe Rust (h264_parameters.rs). Remove emulation-prevention bytes only for legal sequences, bound Exp-Golomb values and require exact RBSP stop/padding. The restricted profile checks High progressive 8-bit 4:2:0, POC type 2, 1-4 references subject to level/DPB macroblock limits, exact coded dimensions and minimal alignment crop, square pixels, explicit limited BT.709/chroma location and timing matching the negotiated FPS. Unsupported interlace, transform bypass, custom matrices, alternate POC, HRD, reorder profile extensions, weighted prediction, slice groups and inconsistent PPS are rejected. Target bitrate is checked against level, not measured as a network ceiling. Existing v9 access-unit, coded sequence, IDR and unchanged parameter-set checks remain. This is deliberately narrower than general H.264; no compatibility fallback. It still does not validate complete slice/CABAC or SEI syntax, prove safe decoder input or enable the normal sharing CLI. The structural transport fixtures include real native SPS/PPS with synthetic slice prefixes and never enter a native decoder.

The new desktop-wgc-live-check diagnostic uses the same loopback-only v9 transport. The native producer starts after the authenticated demand, holds one bounded capture request, and issues immutable origin tokens over a separate in-process channel before sending their wire envelopes. The receiver checks the exact profile, record sequence, coded sequence, keyframe flag and all compressed bytes against its corresponding token. Only the opaque locally generated token can enter the independent native decoder worker; arbitrary network bytes cannot reach CUVID. Ordered transport ACK follows successful native submission, not proof of scan-out. At most eight origin tokens/credits and one queued decode job; no dropped reference pictures. Local diagnostic cancellation returns an error from the consumer, drops the transport futures/channels and joins both native workers. The v8 sharing protocol remains unchanged. This verification channel exists only inside the same-process diagnostic; it is not a proposed remote protocol or a production authentication mechanism.

### Private decoder IPC v1

Only the optional local continuous diagnostic can start the supervised child. This is separate from QUIC and is not a remotely reachable protocol. Fixed 24-byte bootstrap: 8-byte ASCII ILDEC001, existing 12-byte v9 profile (exact 60 FPS, 30 s, 8 Mbps target), big-endian u16 generated sample count 1..180, one-byte NVIDIA DXGI index 0..63 or 255 for unique vendor selection, final reserved byte zero. The child sends exact READY line after initializing inside the required job. Each request has a big-endian u32 length followed by the exact v9 envelope (maximum 2 MiB), validated again by child StreamState. Zero length explicitly cancels before the configured final frame. No unbounded strings or allocations; response lines are capped at 1024 bytes, and a frame's ACK must exactly match its sequence. Full completion automatically flushes only after the configured number of immediate display callbacks and reports native diagnostic counts then DONE; cancellation aborts without EOS and reports DONE with the submitted count. A malformed or missing response ends the diagnostic; no fallback to in-process decode. Parent checks actual process exit in addition to printed markers. Job ownership does not establish a malicious-parent or hostile-driver sandbox.


### Developer-only restricted headless bootstrap

The separate example uses the unchanged strict launcher and an exact nine-byte local bootstrap: opcode 0 plus eight zero bytes (startup), 1 plus the little-endian eight-byte adapter LUID (CUDA/CUVID capability), or 2 plus the same LUID (fixed embedded fixture decode). Reject all other opcodes, unexpected lengths, standalone worker invocation and wrong LUID without fallback. The parent requires an exact bounded success marker and actual zero child exit; there is no caller-supplied compressed data, path or resource handle. This is not ILDEC001, a wire protocol extension, or a remotely reachable command. The existing v8 and local diagnostic v9/ILDEC001 formats remain unchanged.


### v8 local JPEG quality adaptation

The eight-byte configuration still carries the Host-approved JPEG quality value; on a Host with adaptive quality enabled it is the upper bound, with a minimum of 35. JPEG quality is represented by its own JPEG quantization tables, not an extra wire message, so existing v8 viewers still validate the exact same dimensions and mode. Observe outstanding receipts locally before any full-window credit wait; no additional peer command, ACK interpretation or authorization is introduced. Changed records drive a bounded hysteresis policy; lossless tiles and keyframes are unchanged, repeats/no-updates interrupt adaptation streaks. The default Host geometry is now 1080p, with explicit 720p/540p selection. A geometry/codec transition during a v8 session remains invalid. The separate opt-in v10 protocol now implements a versioned adaptive geometry boundary; see [ADAPTIVE-MEDIA.md](ADAPTIVE-MEDIA.md) for exact wire layout, limits and validation.


## Optional negotiated software protocol v11

The separate `intralink/view/11-negotiated` ALPN exchanges a bounded software codec capability mask, a selected configuration, and an exact confirmation after identity validation and before capture. The selected codec is fixed for the session; v10 adaptive geometry and record semantics are unchanged. See [NEGOTIATED-MEDIA.md](NEGOTIATED-MEDIA.md) for the byte layout, local allow-list, and validation. v8/v10 compatibility and v9 isolation remain unchanged.


## Optional bounded software protocol v12

The separate `intralink/view/12-bounded` ALPN adds the viewer's height/FPS ceilings to the v11-style software negotiation. Both endpoints compute the exact intersection and confirm both Host approval and selected profile before capture. Adaptive records and native scaler retargeting remain unchanged. See [BOUNDED-MEDIA.md](BOUNDED-MEDIA.md). Prior wire versions and isolated v9 remain unchanged.
