# Direct connectivity (v0.12)

## Candidate resolution

Default connection uses the saved DNS/IP and port. Numeric IPs bypass DNS; names use a bounded 5-second OS DNS lookup. Select up to four unique IPv4 and four unique IPv6 candidates. The shared Rust policy examines at most 256 answers, normalizes IPv4-mapped IPv6 addresses before filtering and deduplication, preserves resolver order within each family, and rejects zero ports, unspecified, multicast, limited-broadcast IPv4, IPv4 0/8, link-local IPv6 and nonzero IPv6 scope IDs. Interface-scoped IPv6 is not supported. Literal and DNS routes use this policy; transport entry points apply it again before binding or connecting. Loopback remains available for local testing. The endpoint ID never changes with an address change. Iroh direct-only configuration disables relay and address lookup; the transport chooses a path among explicit candidates.

Optional `listen --advertise-lan` advertises one specific private IPv4 socket via `_intralink._udp.local.` with a random instance name and TXT fields `id` (public host endpoint ID) and `protocol=probe-1`. The operator must explicitly approve the host listener after being informed about the privacy effect. No inventory, private key, account token or human device name is advertised. mDNS uses link-local multicast and may be visible on multiple connected interfaces; the preview does not guarantee interface-level confinement. `connect --lan` browses for up to three seconds, filters to the locally pinned ID and protocol, and collects up to four unique private IPv4 hints. It is not an inventory scanner. TXT identity and addresses can be spoofed; authentication is still performed by QUIC. IPv6 mDNS discovery is not implemented; the saved route supports IPv6. If discovery finds no candidate, fails, or the probe fails, the saved route is tried. mDNS registration and cleanup require native LAN testing; an interrupted process may leave cached stale announcements. There is no persistent listener or discovery service.

`connect --attempts 1..3` repeats the direct diagnostic on failure with bounded 2/4 second delays and fresh route resolution. OS DNS caches can retain stale answers; this is not continuous reconnect or QUIC session migration. The host is one-shot and waits at most 120 seconds for an incoming connection; invalid or completed sessions may cause it to stop before a controller retry. Open a new locally approved listener when needed. No silent relay or alternate transport is used.

## Diagnosing NAT

`diagnose --device NAME` reports the saved route, identity and resolved addresses. Optional `--wan-ip` is the router WAN address provided by the operator, not inferred from the controller network. RFC 6598 shared IPv4 (`100.64.0.0/10`) suggests a possible carrier NAT; RFC 1918 WAN addresses suggest upstream private addressing. Neither proves CGNAT. If a WAN IP is supplied, the diagnostic compares it with the selected candidates of the same canonical address family, reporting a match, difference, absence of same-family candidates or invalid input. A match does not prove reachability; a mismatch can result from stale DNS, upstream NAT, multiple interfaces, or normal differences between a router WAN IPv6 address and a host IPv6 address. Only the selected candidates are compared, not every DNS record. No external IP service is contacted. IPv6 may be globally addressed but filtered. An address classification or DNS response is not a reachability test. Use an approved QUIC probe to test actual reachability and peer identity. No STUN, ICE, NAT type detection, hole punching, firewall modification or port mapping is implemented. A future design needs explicitly configured authenticated signaling and owner-operated optional relay for unreachable networks. No guaranteed 100% connectivity without those mechanisms.

## DDNS provider boundary

The DuckDNS adapter is isolated from identity, grants and routing; other provider implementations can be added without trusting the provider for authentication. The CLI implements DuckDNS only. Owner-created record required. The HTTPS update operation uses one label, prompts for the account token, does not persist the token, refuses redirects, bypasses system proxies and sanitizes errors. One-shot explicit IPv4, IPv6 or dual-stack updates follow the documented DuckDNS API. Optional foreground `--interval` (60–3600 seconds) is available only when the provider detects IPv4; it retries later if a subsequent refresh fails. Initial failures stop the command. IPv6 must be explicitly supplied in a one-shot update. Run on the intended host network or owner router, not an unrelated controller network. Provider requests, OS and library instrumentation may handle sensitive token copies; avoid debug tracing or proxy interception. No DNS registration, automatic token provisioning, provider failover or verified automatic IPv6 detection is delivered.

## Capability-specific LAN discovery and visual input selection (2026-11-28)

The current Windows input-preview build supports `input workspace --choose` (automatically selects the spatial pad). Unlock the local BASE profile in the no-echo terminal. The native selector lists only authenticated vault outbound records, up to 128 local records across eight-card pages, with up to eight selected devices. The first bounded LAN browse starts when the selector opens; Refresh replaces the previous observation. An announcement is only a routing hint, never a connected or authorized status. A missing announcement does not mean offline: the saved route remains available. No new peer, profile, grant, listener or input session is created by discovery or selecting cards. Continue requires a complete focused click and a nonempty selection after discovery completes. Disabled controls cannot activate when the scan finishes under a held button. Escape, Cancel, or close stops the UI and waits for the bounded owned daemon cleanup. The existing explicit local APPROVE, peer pinning and CLIENT session approval remain; the spatial pad still starts SAFE.

On Windows and Linux X11 input builds, CLIENT can explicitly use `input host --bind HOST_PRIVATE_IPV4:45100 --controller base --seconds 300 --advertise-lan`. The privacy disclosure precedes input consent, native stop indicator and private IPv4 bind. A separate `protocol=input-1` DNS-SD TXT tag distinguishes this from `probe-1`; no screen/input permission follows from the tag. Only a randomized instance name, public endpoint identity and private route are advertised. No device name, secret, keypress, vault path or pairing code is sent. Endpoint and owned-input release precede advertisement cleanup. An abrupt kill can leave stale cached announcements; discovery never proves liveness. Existing probe advertisements are unchanged.

BASE may instead use `input workspace --device NAME --lan` (Windows or Linux X11). It performs one finite browse for the selected paired IDs before the normal input workspace approval. No automatic advertisement or scanning occurs in legacy CLI mode without the new explicit options. The shared collector accepts only exact saved identities and the requested protocol, private IPv4 and nonzero port. It limits the scan to three seconds, at most 1024 events, 32 addresses per resolved event, 128 identities and four unique hints per identity, followed by bounded daemon shutdown. Up to four private candidate addresses are passed to the existing pinned QUIC input handshake, retaining at least one valid saved route if available. No persisted route update, implicit grant, relay, public input, remote discovery of unknown peers, continuous background scan or auto-reconnect. The user must still separately pair unknown devices, approve the CLIENT and activate the BASE pad. Linux X11 retains its explicit CLI device selection; Android input advertisement, QR camera import, graphical screen-workspace selector, physical edge switching and physical multi-device acceptance remain pending. The Windows selection window still uses terminal vault unlock and approval. See benchmarks/kvm-lan-selector-20261128.txt.
