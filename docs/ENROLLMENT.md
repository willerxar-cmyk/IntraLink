# Offline enrollment v1 (development preview)

This is a locally authorized exchange for diagnostic-only grants, not a bearer token, remote enrollment service, account invitation or production identity protocol. The operators verify both full public IDs independently, using a trusted channel. A self-signed offer only proves possession of its stated key, not ownership by a particular person.

## State transition

1. The controller exposes its public identity using `identity`. The host operator verifies it, enters an explicitly chosen DNS/IP and port, and creates an offer (`invite`). The encrypted host vault now holds one pending body; it does not authorize incoming sessions yet.
2. The controller operator pastes the offer (`accept-invite`), checks both identities and route, confirms locally, and saves an outbound grant and consumed nonce. The controller signs the exact same invitation body under an acceptance-specific signature domain. It returns this code to the host.
3. The host operator uses `confirm-invite`, verifies the controller signature and expiry and approves locally. The signed acceptance body must equal the pending body. A successful save atomically consumes the pending offer and adds the inbound grant.
4. An offer can be replaced or canceled. Revoke existing grants separately. If the acceptance is lost, canceled or expired, revoke the controller-side outbound grant and begin a fresh exchange. Do not interpret a local outbound grant as proof that the host confirmed it.

Offer and acceptance start with `IL1I.` and `IL1A.` respectively, followed by unpadded URL-safe Base64 of a strict JSON document: `invitation` plus `signature`. The signature is a 64-byte Ed25519 signature encoded as unpadded URL-safe Base64. The versioned invitation contains host ID, controller ID, DNS/IP route, port, a random 16-byte nonce, creation and expiration in Unix UTC seconds, and version. The signed bytes are the domain prefix `intralink/enrollment/v1/`, the exact code prefix, a NUL byte, and Rust serde JSON serialization of the typed invitation. The receiver reserializes the typed fields to verify the signature. This is a Rust implementation format; cross-language canonicalization and protocol stability are not promised. No private key or bearer password appears in the code.

Bounds: 2,048 bytes of input code, TTL 60–900 seconds (default 300), one pending offer per profile, at most 128 recent consumed nonces on the controller. The clock must be synchronized; no future-created or expired invitation is accepted. Local approval is checked before mutation is saved, and expiry is checked again at the mutation. No replay protection across old vault restores or malicious clock rollback; both need explicit production defenses. Host revocation remains local. Both endpoints must remove outdated grants after recovery. Code text/QR is signed but not encrypted and discloses public IDs, route and timestamps; keep it off public channels. The QR can be generated in terminal text or the opt-in native graphical window described below. Camera scanning and mobile signed enrollment are not included. Copy the exact text if a QR cannot be read reliably.

Authorization remains restricted to the fixed probe. The new grants do not enable file access, remote terminal, remote desktop or input. The host still needs the local operator to start a one-shot listener. Before enabling additional capabilities: compile and run all tests, fuzz code parsing, exercise expiry/replay/cancel/replace with real vaults, audit signature validation and recovery, and implement explicit capability policy.

## Graphical signed enrollment (2026-11-28)

Desktop-preview Windows/X11 builds accept the opt-in `--gui` flag for `invite`, `accept-invite`, `confirm-invite` and `connection-card`. The graphical review presents both complete 64-digit hex identities, full validated routing host (up to 253 ASCII bytes, wrapped without truncation), UDP port, validity/expiry, scope and local peer label. Exact lowercase/case-sensitive values are also printed in the terminal; the compact bitmap font renders labels and hexadecimal digits in uppercase. Confirm identity ownership independently over a trusted channel; a self-signed code does not establish human ownership. Check the verification box or release Space, then use the distinct confirmation button or release Enter. Escape, Cancel, window close or deadline aborts without saving; loss of window focus clears verification and held-control state. Already-held, mixed mouse/key or overlapping gestures cannot approve. New invitation review lasts at most 300 seconds; existing invitation review also stops at actual expiry. The signed accept/confirm code is verified by the existing Rust vault and checked again at mutation. No network access, listener, camera, clipboard read, screen/input authorization or new protocol is introduced by these windows.

A generated QR uses the complete existing signed offer/acceptance, integer module scaling and a four-module quiet zone. Generate the QR before the local encrypted write; after successful save print the exact code and show the window. The window closes at actual expiry or at most five minutes. A presentation failure after saving is reported explicitly and does not claim a rollback. The public `connection-card --gui` uses the same renderer but is prominently labeled unsigned and no access grant. Closing a displayed code does not revoke an issued offer or saved grant; use the existing cancel/revoke commands when needed. Passwords remain in the local no-echo terminal; after saving, the password and profile are dropped before displaying the code. The local vault lock stays held until the window closes. Existing terminal text and terminal `--qr` workflows remain; `--qr` and `--gui` are mutually exclusive. No native camera reader or mobile signed-invite integration yet: transfer the exact text through a trusted channel or use an independently trusted reader and paste the payload, never a shortened identity. Android's existing unsigned connection-card workflow remains separate. This is a graphical review/QR display, not a completely terminal-free wizard.

Example: after both devices have exchanged and verified full public identities, use on CLIENT `intralink invite --controller-id BASE_PUBLIC_ID --host CLIENT_PRIVATE_IPV4 --port 45100 --gui`; transfer the signed offer. On BASE `intralink accept-invite --name client --gui`; transfer the signed acceptance. On CLIENT `intralink confirm-invite --name base --gui`. The three operations create only the existing directional pairing records. Each actual session still needs its separately authorized capability. See benchmarks/kvm-graphical-pairing-20261128.txt.
